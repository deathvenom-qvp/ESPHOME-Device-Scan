# ESPHome Device Scan

A Home Assistant add-on repository containing **ESPHome Device Scan** — an
add-on that finds ESPHome devices with no YAML config, matches each to the
**parent config already in your ESPHome directory**, and generates a per-device
config with the real device name and the MAC-suffix logic resolved.

No templates are shipped and nothing is copied into your config. The parent it
builds from is the same file you flashed the batch with.

## Install

[![Open your Home Assistant instance and show the add add-on repository dialog with a specific repository URL pre-filled.](https://my.home-assistant.io/badges/supervisor_add_addon_repository.svg)](https://my.home-assistant.io/redirect/supervisor_add_addon_repository/?repository_url=https%3A%2F%2Fgithub.com%2Fdeathvenom-qvp%2FESPHOME-Device-Scan)

Or by hand: **Settings → Add-ons → Add-on Store → ⋮ → Repositories**, add
`https://github.com/deathvenom-qvp/ESPHOME-Device-Scan`, then install
**ESPHome Device Scan**.

## The problem it solves

Flash a batch of boards from one base firmware and they all show up on the
network — but each still needs its own YAML in `<config>/esphome/` before it can
be maintained or updated. That base config almost always carries MAC-suffix
logic, either ESPHome's `name_add_mac_suffix: true` or a `${mac}` substitution,
which has to be resolved to a real fixed name in the per-device file.

This add-on does that pass automatically, on a schedule.

### Worked example

Parent `/homeassistant/esphome/cloudbay-t.yaml` — already there, unchanged:

```yaml
substitutions:
  devicename: cloudbay-t
  mac: "000000"

esphome:
  name: cloudbay-t-${mac}
  friendly_name: "${friendly} ${mac}"
  name_add_mac_suffix: true

wifi:
  ssid: !secret wifi_ssid          # untouched
  ap:
    ssid: "${devicename}-${mac}"   # captive portal
```

The `${mac}` in its name is what marks it a parent — no directive needed.
Discovered device `cloudbay-t-livingroom`, MAC `AA:BB:CC:DD:EE:FF`, written
alongside it as `cloudbay-t-livingroom.yaml`:

```yaml
# Generated by ESPHome Device Scan from a base template.
# Template: cloudbay-t.yaml
# Device:   cloudbay-t-livingroom
# MAC:      AA:BB:CC:DD:EE:FF
# Safe to edit: a scan never overwrites this file.

substitutions:
  devicename: cloudbay-t-livingroom
  mac: "ddeeff"

esphome:
  name: cloudbay-t-livingroom
  friendly_name: "CloudBay T Living Room"
  name_add_mac_suffix: false

wifi:
  ssid: !secret wifi_ssid          # untouched
  ap:
    ssid: "${devicename}-${mac}"   # captive portal
```

Five lines changed. The comment, the `!secret` tag, the blank lines, the key
order and the quoting style are all byte-identical — the generator locates
values with a YAML parser but patches the original text rather than
re-serialising it.

Example parents are in [`esphome_device_scan/examples/parents/`](esphome_device_scan/examples/parents/)
and their worked outputs in [`esphome_device_scan/examples/generated/`](esphome_device_scan/examples/generated/).
They are documentation and test fixtures only — the add-on never installs them.

## What it does

- **Discovers** ESPHome devices from Home Assistant's device registry, entity
  registry and config entries, including MACs and in-progress discovery flows.
- **Finds parents in place** — a base config is recognised by its MAC-suffix
  logic (`${mac}` in the name, or `name_add_mac_suffix: true`), or by an
  explicit `# x-template: true`. Parents are never counted as a device's
  config, and are never written over.
- **Checks** for an existing config in both the ESPHome YAML directory (by
  parsing each file's declared `esphome.name`, substitutions resolved) and
  ESPHome's `.esphome/storage/*.json` sidecar index.
- **Matches** devices to parents by the family in the parent's own name
  (`cloudbay-t-${mac}` claims `cloudbay-t-*`), or by explicit prefix, regex or
  model directives — deterministically, with a documented precedence order.
- **Generates** `<node-name>.yaml`, resolving the name and MAC-suffix logic and
  preserving everything else.
- **Never overwrites.** Automation only ever creates. Regeneration is an
  explicit click and takes a timestamped backup first.

## Panel

An ingress panel lists every device with its node name, MAC, connection status,
whether it has a config and which parent matched, plus **Preview**,
**Generate**, **View** and **Regenerate** actions and a live activity log.

**Regenerate all** rebuilds every matched device from its parent in one go —
for after you have edited a parent. It shows what it will touch first, calls
out any config you wrote or edited by hand, and offers to skip those. Every
replaced file is backed up.

Parents can also be ticked individually, with **Regenerate selected** and
**Regenerate & flash selected**. The second hands each config to the **ESPHome
Device Builder** add-on to compile and upload over the air, one device at a
time, with a progress dialog showing the live build log.

Full documentation: [`esphome_device_scan/DOCS.md`](esphome_device_scan/DOCS.md).

## Development

```bash
cd esphome_device_scan
pip install -r requirements.txt
pip install pytest pytest-asyncio ruff

pytest -q                              # 318 tests
ruff check app/ scripts/ tests/

# Offline dry run, no Home Assistant needed. Put a parent in the directory
# first; parents and generated children share it.
python3 -m app --once --dry-run --esphome-dir /tmp/esphome

# Refresh the golden example outputs after an intentional generator change
python3 scripts/refresh_examples.py
```

To confirm the Home Assistant WebSocket payloads on your own instance:

```bash
docker exec addon_<slug> python3 /opt/edscan/scripts/probe_ha.py
```

### Layout

```
app/
  models.py         frozen domain types
  settings.py       options.json + EDSCAN_* env -> Settings
  ha_client.py      HaApi protocol + Supervisor-proxy implementation
  discovery.py      registries -> Device list
  config_store.py   ESPHome config dir: index, atomic write, backup
  esphome_dashboard.py  ESPHome Device Builder client (build + OTA)
  flashing.py       flash session state, progress, cancellation
  parents.py        the one rule for what counts as a parent template
  templates.py      parent discovery + the matching engine
  yaml_compat.py    ESPHome-tag-tolerant parsing, node -> source offsets
  patching.py       text edit primitives
  generator.py      the generation engine (pure)
  orchestrator.py   scan policy: what gets generated, and what never does
  scheduler.py      the periodic loop
  web/              ingress panel (aiohttp + vanilla JS)
```

Collaborators are constructor-injected throughout, so the whole pipeline runs in
tests against a fake Home Assistant and a temp directory — no network, no clock.
